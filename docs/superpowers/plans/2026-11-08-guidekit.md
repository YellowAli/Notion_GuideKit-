**Problem (from the author's club):** Notion is hard to learn at the start, and new users don't know how to do simple tasks. GuideKit walks them through doing the task themselves.

## Decisions

Made by the user:
- Reusable library for multiple teams is the headline.
- **No LLM.** End users start tutorials from "Walk me through X" buttons. Engineers write flows themselves.
- The mock app is Notion-themed.
- During a walkthrough, only the highlighted control responds. Taps elsewhere are blocked and nudge the tooltip; an always-visible Exit button ends the guide.

Claude's calls (overrule any of these):
- Real Notion app is out of scope: iOS sandboxing prevents overlaying or reading another app, and App Store builds don't run in the Simulator.
- Notion theme means its visual style (clean off-white pages, block layout, restrained typography, similar menus). No Notion logo or wordmark; README and app's about line label it an unofficial concept demo.
- No per-team manifest (user-approved). A team's only inputs are tags, flow files, and occasional facts. Names link by exact lookup at runtime; the automated UI test catches mistyped names, reporting flow, step, and the missing name.
- No CLI. Its only real job depended on the manifest.
- Each team's module is its own Swift package depending only on GuideKit and the shared DesignSystem package. That is the reuse proof.
- Tagging lives in shared components (user-approved): `AppButton` and `AppMenuRow` take an optional `guideID`, so product code passes a name and never writes GuideKit view code. One-off custom controls call `.guideTarget` directly.
- Public reporting says Notion is migrating its iOS UI to SwiftUI, with the editor reported as web-based as of 2025. The README frames fit to Notion as based on public reporting only.
- Tags over server-driven UI (incrementally adoptable in an existing app; devices own the real state anyway). Mention in README as a considered tradeoff.
- Flows are authored as JSON. Tap-only steps in v1. iOS 17+, Swift 6 tools with language mode 5 to avoid a concurrency detour. No third-party dependencies.

## Non-goals

Any LLM integration (README may note that flows being plain data leaves that door open); overlaying the real Notion app; text-entry steps; targets inside system sheets/popovers (they present above the root overlay, so demo menus are in-hierarchy; document the limitation); fading guidance; server-driven UI; claiming any user metrics that weren't measured.

## Architecture

```text
Team writes: tags in views, flows/*.json, occasional facts
        ↓
   FlowValidator                           (structure only; at load in DEBUG and in unit tests)
        ↓
   "Walk me through…" menu (lists every registered flow)
        ↓
   GuideRuntime ←── live targets + facts   (pure state machine, no UI knowledge)
        ↓
   SpotlightOverlay (human)  |  XCUITest driver (automated)
```

### How a step works

**1. Finding the component: it registers itself.** GuideKit never searches the screen. Shared components apply `.guideTarget` when given a `guideID`. `.guideTarget` publishes an anchor preference; `.guideHost()` collects them and resolves a live `[ID: [CGRect]]` map with a `GeometryReader`. A step looks up its ID. No entry means not rendered yet, so the runtime waits until its timeout.
- Repeated rows share a role ID and may pass `instance:`. A step may set `"pick": "first" | "last"` (default `first`, tree order).
- Scrolling: `.guideScrollContainer()` on a `ScrollView` lets the host bring a rendered, off-screen target into view. Unrendered lazy rows are a v1 limitation.
- Sheets/popovers are outside the root overlay: v1 keeps demo menus in-hierarchy and documents this. A per-presentation `.guideHost()` is the future path, as is a UIKit adapter registering a `UIView`.
- Not built in v1: accessibility-tree lookup (labels can be translated, duplicated, or vague, and reading the tree in-process is unverified) and a DOM resolver for web-based surfaces. README notes both as future resolvers that wouldn't change flows.

**2. Highlighting it: a dimmed layer with a hole.** The host draws one root overlay: a dark `Path` with an even-odd rounded cutout at the target's frame (padded), a pulsing ring (static under Reduce Motion), and a tooltip placed above or below by available room. Frames come from the live map, so the hole follows layout changes and animates between steps. Each instruction is announced to VoiceOver.
- Blocking: the dim layer uses `.contentShape(cutoutPath, eoFill: true)`, so it receives taps everywhere except the hole. Taps in the hole reach the real control; taps elsewhere nudge the tooltip.

**3. Knowing it worked: watch the result, not the tap.** Each step declares one `completeWhen` check. Prefer them in this order:

| Check | Meaning | Team effort |
|---|---|---|
| `targetVisible` | A named target appeared (for example, a menu option) | None |
| `fact` (`equals`, `increasedBy`) | App state changed as expected; baseline captured on step entry | One `.guideFact` line |
| `tapped` | The target was tapped; fallback when nothing observable changes | None, weakest proof |

`tapped` attaches a simultaneous gesture to the target only while that step is active.

### Core contracts

**Feature registration:** `GuideFeature(namespace: "calendar", bundle: .module)` loads that package's `flows/*.json`.

**Flow:** steps run top to bottom, one active target at a time. `title` is the button text in the menu.

```json
{ "id": "editor.add_todo", "title": "Add a to-do", "steps": [
  { "target": "editor.add_block_button", "say": "Tap + to open the menu",
    "completeWhen": { "targetVisible": "editor.block_menu_todo" } },
  { "target": "editor.block_menu_todo", "say": "Choose To-do",
    "completeWhen": { "fact": "editor.todo.count", "increasedBy": 1 } } ] }
```

**FlowValidator:** structure only; returns all errors, not just the first: empty flow, duplicate/malformed ID, ID outside the team's namespace, malformed condition. Unknown targets and facts surface at runtime as named failures (for example, "`calendar.create_event` step 1: target `calendar.new_evnt` not found"; "fact `calendar.event.count` was never reported"; "`increasedBy` used on a bool fact").

**GuideRuntime:** pure reducer, `handle(event) -> [Effect]`.
- Events: `start`, `factsChanged`, `targetsChanged`, `targetTapped`, `timeout`, `cancel`.
- States: `idle`, `waiting(step, baseline)`, `completed`, `failed(reason)`.
- Effects: `present(step, frameTargetID)`, `dismiss`, `scheduleTimeout`.
- Blocking removes off-script recovery. A target that never appears, or a check that doesn't pass after the tap, fails with a named reason; the user sees a short "couldn't continue" message and the guide exits. Idle users never time out.

**View API** (all a team writes in UI code):

```swift
AppButton("+", guideID: "editor.add_block_button") { ... }
CustomControl().guideTarget("editor.custom")   // one-off views only
PageView().guideFact("editor.todo.count", value: todos.count)
AppRoot().guideHost(features: [EditorFeature.guide, CalendarFeature.guide])
```

`.guideTarget` publishes the frame through an anchor preference and also sets `accessibilityIdentifier`, so tests find the same ID. `GuideMenu` is an in-hierarchy panel that lists every registered flow as "Walk me through: <title>", so a team's new flow appears with no menu code.
**Test driver:** runs in the app's real runtime so verification logic isn't duplicated. Launched with `GUIDEKIT_TEST_FLOW=<id>`, the app exposes a hidden accessibility element `guidekit.status` containing JSON (`currentStep`, `target`, `state`, `failure`). `FlowTestDriver`: read status → tap target through the real overlay → wait for advance → attach screenshot → repeat until `completed`; on failure, report flow ID, step, and reason. A single helper runs every registered flow.

### Task 3: Runtime state machine

**Files:** Create `Sources/GuideKitCore/GuideRuntime.swift`, `Tests/GuideKitCoreTests/GuideRuntimeTests.swift`.

**Interfaces (consumes Task 1; produces):**
```swift
public enum GuideFailure: Error, Equatable, CustomStringConvertible {
  case targetNotFound(flowID: String, step: Int, target: String)
  case factNeverReported(flowID: String, step: Int, key: String)
  case wrongFactType(flowID: String, step: Int, key: String)
  case checkNotPassed(flowID: String, step: Int)
}
public enum GuideState: Equatable { case idle, waiting(flow: Flow, step: Int), completed(flowID: String), failed(GuideFailure) }
public enum GuideEvent { case start(Flow, targets: Set<String>, facts: [String: FactValue])
  case factsChanged([String: FactValue]), targetsChanged(Set<String>), targetTapped(String), timeout(token: Int), cancel }
public enum GuideEffect: Equatable { case present(step: Int, Step), dismiss, scheduleTimeout(token: Int) }
public struct GuideRuntime { public init(); public private(set) var state: GuideState; public mutating func handle(_ event: GuideEvent) -> [GuideEffect] }
```
Failure text uses step numbers starting at 1: `` `calendar.create_event` step 1: target `x` not found ``.

**Rules the implementation must follow:**
- On step entry, capture the `factIncreased` baseline. If the fact is absent, the first report sets it. If it isn't an int, fail `wrongFactType`.
- A check that is already true on entry is disarmed; a tap on the step's target arms it. Otherwise it's armed from the start.
- Tokens increase with every schedule; stale tokens are ignored.
- Schedule a timeout on entry only if the target is absent, and on every tap of the current target.
- On a current timeout: target absent → `targetNotFound`; no tap yet → ignore; tapped with a missing fact → `factNeverReported`; else `checkNotPassed`.
- `.start` while `.waiting` is ignored. `.cancel` → `.idle` + `.dismiss`. Last step passing → `.completed` + `.dismiss`.

- [ ] **Step 1:** Write tests: `testHappyPathAdvancesAndCompletes`; `testTargetVisiblePasses`; `testFactEqualsPasses`; `testFactIncreasedUsesBaseline` (start at 3; 3 doesn't pass, 4 does); `testTappedPassesOnlyForCurrentTarget`; `testAlreadyTrueCheckWaitsForTap`; `testIdleUserNeverTimesOut` (target present, no tap, `.timeout` leaves state unchanged); `testMissingTargetFailsOnTimeout`; `testTapThenNoChangeFailsCheckNotPassed`; `testMissingFactFailsFactNeverReported`; `testWrongFactTypeFails`; `testStaleTimeoutIgnored`; `testSecondStartIgnored`; `testCancelDismisses`; `testFailureDescriptionNamesFlowStepAndTarget`.
- [ ] **Step 2:** Implement; run `swift test --filter GuideRuntimeTests`; expect PASS.
